  The Shapes of AI Data: A Companion Guide for COSC 2060

In data science and artificial intelligence, there is no single "data structure." The way you engineer, clean, and format a dataset depends entirely on the downstream AI task or system interface.

Coming from introductory SQL (CMAP 1815), you are used to normalization—splitting data into many related tables to avoid redundancy. But AI models and agent tools cannot read normalized schemas directly. They require flattened feature matrices, normalized tensors, searchable vector chunks, and strict JSON contracts.

This guide maps the exact eight data shapes and infrastructure layers you will build in COSC 2060, unit by unit, so you always know what you are building and why it is shaped that way.

  1. Unit 1 — Supervised Learning: Tabular Feature Matrices

Supervised learning is like teaching with an answer key. The model looks at historical examples (the input features X) and learns to map them to a known outcome (the target label y).

       Features (Inputs, size D)               Target (Output)
   [ Feature 1,  Feature 2, ... Feature D ]      [ Label (y) ]
Obs 1 [   x1,1    ,    x1,2   , ...   x1,D   ]  ->   [   y1    ]
Obs 2 [   x2,1    ,    x2,2   , ...   x2,D   ]  ->   [   y2    ]
Obs N [   xN,1    ,    xN,2   , ...   xN,D   ]  ->   [   yN    ]

  What You Build in Unit 1

Using DuckDB and Apache Parquet, you combine separate relational tables (driver rosters, truck routes, and hourly weather logs) into one flat 2D feature matrix saved as feature_matrix.parquet.

​

Engineering Notes & Design Considerations

  • Preventing Time-Travel Leakage: Use temporal ASOF JOIN queries so every route only sees weather recorded at or before departure time—never future observations.
  • Point-in-Time Aggregations: Compute rolling driver history with SQL window functions (OVER (PARTITION BY ... ORDER BY ...)) using strict ROWS BETWEEN bounds.
  • Columnar Storage: Export the finished matrix to Parquet instead of CSV so data types, compression, and fast column scans are preserved.

  2. Unit 2 — Unsupervised Anomaly Detection: Scaled & Encoded Matrices

When you do not have a pre-labeled "fraud" column, unsupervised anomaly detection models (like IsolationForest) measure mathematical distance between rows to spot outliers. Every column must be numeric and on a comparable scale.

Raw Row:    [ gallons=85.0, implied_speed=1266.7, region="West" ]
Engineered: [ gallons_z=0.42, speed_z=18.90, region_West=1, region_East=0 ]

  What You Build in Unit 2

Using Polars lazy scanning (pl.scan_parquet), you process 1,000,000 fuel card swipes, engineer velocity features with .shift(1), apply Z-score standardization and One-Hot Encoding, and feed the clean numeric matrix into an anomaly detector.

​

Engineering Notes & Design Considerations

  • Scale Dominance: Without Z-score scaling, a column measured in thousands (odometer) will drown out a column measured in tens (gallons).
  • Lazy Execution: Polars optimizes filter pushdown and streaming so 1M+ rows run in seconds without exhausting laptop RAM.
  • Null Safety: Window operations like .shift(1) produce null on the first row per driver; always handle nulls explicitly with .fill_null(0.0).

  3. Unit 3 — Computer Vision: Image Tensors & YOLO Bounding Boxes

Vision models do not see "pictures"—they process fixed-size 3D numerical arrays (Height × Width × Channels) paired with normalized bounding-box label files.

Image Tensor: shape=(640, 640, 3), dtype=uint8 (Letterboxed RGB/BGR)
YOLO Label:   class_id  x_center  y_center  box_width  box_height  (all in 0.0..1.0)

  What You Build in Unit 3

Using OpenCV and NumPy, you scan raw truck inspection images of mixed resolutions, apply letterbox padding to a uniform 640 × 640 canvas without squishing objects, and transform pixel bounding boxes into normalized YOLO .txt coordinates.

​

Engineering Notes & Design Considerations

  • Aspect-Ratio Preservation: Never stretch a 16:9 camera frame into a square; scale uniformly and pad borders with neutral gray (114, 114, 114).
  • Coordinate Re-mapping: Whenever you scale and pad an image, you must shift and re-normalize its bounding boxes to match the padded canvas.
  • Channel Order Awareness: OpenCV loads images in BGR order, while most deep learning models expect RGB.

  4. Unit 4 — Unstructured Text & Vector Search (RAG)

Large Language Models have fixed context windows and cannot query raw PDFs or maintenance logs efficiently. Retrieval-Augmented Generation (RAG) splits documents into overlapping chunks, converts each chunk into a dense embedding vector, and stores them alongside filterable metadata.

{
  "id": "manual_sec4_chunk02",
  "text": "Replace brake pads if rotor thickness drops below 18mm...",
  "embedding": [0.021, -0.144, 0.089, ...],
  "metadata": { "doc_type": "maintenance", "vehicle_class": "heavy" }
}

  What You Build in Unit 4

Using Regex, semantic chunking, and ChromaDB, you clean noisy maintenance text, split it into context-preserving chunks, and build a hybrid search index combining metadata filters with vector similarity.

​

Engineering Notes & Design Considerations

  • Chunk Overlap: Overlapping consecutive chunks by 10–20% prevents sentences or safety thresholds from being cut in half.
  • Metadata Pre-Filtering: Filter by vehicle_class or year before running vector similarity so you retrieve relevant, accurate facts faster.

  5. Unit 5 — Data-as-a-Service: Validated JSON REST APIs

Clean datasets sitting in a local folder cannot power live dashboards or apps. In Unit 5, data becomes a live service exposed over HTTP with strict input/output schemas.

POST /predict/delay  ->  Pydantic Request Validation  ->  JSON Response (HTTP 200)
{ "driver_id": 42, "distance_miles": 320.5 }       { "risk_score": 0.14, "status": "ok" }

  What You Build in Unit 5

Using FastAPI and Pydantic v2, you wrap your data layer in GET and POST endpoints with automatic type validation, clear HTTP error codes (422 / 404), and automated pytest endpoint tests.

  6. Unit 6 — Agentic Interfaces: Deterministic MCP Tool Schemas

AI agents should never write raw, unrestricted SQL against production databases. Instead, data engineers expose deterministic, read-only tool functions with strict parameter guardrails using the Model Context Protocol (MCP).

Agent Request -> MCP Tool: get_driver_safety_summary(driver_id: int, limit: int = 10)
             -> Guardrail Check (read-only, bounded limit) -> Structured JSON Result

  What You Build in Unit 6

Using the Python MCP SDK, you build safe tool registries with type-checked inputs, row limits, and sanitized outputs so an AI assistant can query fleet data reliably without hallucinating schemas or leaking secrets.

  7. Unit 7 — Pipeline Orchestration: Asset Dependency Graphs (DAGs)

Real pipelines run on schedules and fail when networks blip. Rather than brittle cron scripts, modern orchestration models data assets as a Directed Acyclic Graph (DAG) where downstream steps only run after upstream assets succeed.

[raw_trips] ---\
                +--> [joined_features] --> [trained_model]
[clean_weather]/     (with retries, Dead-Letter Queue, & idempotent partitions)

  What You Build in Unit 7

Using Dagster patterns and GitHub Actions, you implement topological execution ordering, exponential backoff retries, Dead-Letter Queues (DLQs) for bad rows, and idempotent re-runs.

  8. Unit 8 — Production Packaging: Docker & Capstone Defense

Code that only works on your laptop is not production engineering. In the final unit, you package your data pipeline, tests, and dependencies into a reproducible Docker container and defend your architecture against a blind evaluation batch.

Dockerfile (Multi-Stage) -> Reproducible Image -> pytest Verification -> Stakeholder Pitch
​

Data Engineer's System Architecture Checklist

  •   Identity Integrity: Does every observation have a clean, non-null, immutable primary identifier (such as driver_id, trip_id, or chunk_id)?
  •   Handling Null Values: Are missing parameters dropped or imputed explicitly with documented defaults?
  •   Format Compression: Is analytical data stored in typed, columnar Parquet instead of bloated CSVs?
  •   Data Lineage & Idempotency: Can you trace every output back to its source table and re-run the pipeline safely without creating duplicates?
